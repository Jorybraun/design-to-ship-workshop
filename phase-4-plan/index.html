Phase 04 · Planning + Linear

Plan the work.
Then delegate.

Choose a technical approach. Break it into small visitor-facing changes. Review the tickets before putting them in Linear—or asking Devin to build.

Lesson, not live project approval. The DesignCraft documents are teaching examples. Opening this page creates no issues, branches, PRs, or conference application. Use your actual approved inputs, or explicitly choose a hypothetical rehearsal.

01 · Say / do / decide

Rehearse the handoff.

Core path: plan in chat, review one ticket, then inspect Linear read-only. Publishing and stacked PRs are extensions—not prerequisites for learning to plan.

01 / Confirm what is actually approved

Say: “Before we tell Devin how to build, let’s check what we have agreed to build.”

Do: attach the approved SPEC.md, DESIGN.md, actual assets/specimen/prototype, and intended application directory. Do not point at website/ as though it were the conference app.

Decide: real project planning or hypothetical DesignCraft rehearsal? Missing approval or design assets are blockers, not an invitation to invent them. Stop until the scope is clear.

For the teaching-only trial, say:

Discuss the DesignCraft teaching examples in chat only. Treat them as fictional and unapproved. Do not run MCP, write files, or implement anything. Identify the first real-build blocker and one consequential planning question; wait for my answer.

Use the example spec, design handoff, and candidate plan as discussion material. Rehearsed answers do not authorize a real build.

02 / Ask for an approach, not code

Say: “Architecture means where the pages, data, interactions, and checks will live. We want the simplest approach that meets the spec.”

Do: enter /plan in Devin CLI, confirm the active mode, and paste Prompt 1. UI controls can differ by client; use /help if needed.

Expect: inspected facts, two viable options where meaningful, a recommendation, risks, and one consequential question at a time. Decide: the approach and target directory. No dependencies installed; no files edited.

03 / Turn requirements into reviewable slices

Say: “Don’t give me ten technical chores. Give me changes a visitor can try, each with a definition of done.”

Do: paste Prompt 2 after architecture approval. Read the first ticket aloud. Ask: “What can I demonstrate? What blocks it? What proves it works?”

Expect: requirements mapped to tickets, explicit dependencies, testable acceptance criteria, exclusions, and a PR boundary. Stop: approve or revise the ticket list before publishing.

04 / Inspect Linear before writing to it

Say: “Linear is our shared record of work. MCP gives the agent a connection; it does not decide what the agent may change.”

Do: choose the exact workspace, team, and project; paste Prompt 3. See connection setup and fallback.

Expect: available tools, relevant existing issues and statuses, and a duplicate check within the selected scope. No broad workspace browsing. Stop: authentication or authorization problems go back to the human.

05 / Publish only the reviewed batch, optionally

Say: “Show me exactly what you will create, where, and how many. Creating a ticket is not permission to start work.”

Do: use Prompt 4 to preview the batch. Confirm payloads, status, count, and dependency edges explicitly. Only then leave Plan mode and authorize that operation with appropriate write access.

Check: read back actual issue IDs, links, fields, and blockers. On partial failure, reconcile what exists before any retry. Stop: no code, assignment to an agent, branch, push, PR, or deployment.

First live question

What are we planning from?

“Use DesignCraft for a hypothetical rehearsal” is different from “these files and assets are approved for implementation.” Name the choice before proceeding.

Bad ticket

Build the schedule.

No scope, missing states, no completion check. The agent has to guess what “done” means.

Better ticket

Visitors can filter talks by track.

Eight talks under All; four per track; selected state exposed accessibly; ordered time groups; empty cases; reload resets to All. Include fixtures, responsive checks, and exclusions in the same slice.

A real planning catch

Resolve the empty-state precedence.

The example spec leaves a decision: if all talks are absent while Product is selected, which message wins? The skills chapter demonstrates this review. A suggested answer is not approval. Resolve it before the schedule ticket is ready.

Optional demonstrations · not required for the core build
  • Figma MCP: introduced in Phase 3 if a connection is available; read-only inspection before specific remote-write authorization.
  • Subagents: delegate a bounded research or independent task, then inspect its findings. Parallel workers are not a reason to ignore dependencies.
  • Cloud delegation / native Linear integration: demonstrate separately with configured accounts. A Linear MCP issue write does not itself launch a cloud Devin session; existing workspace automation must be checked.

Skills explain a method. MCP exposes external tools. Plan mode changes how the agent works. Tests provide evidence. None of these substitutes for the participant's decisions.

03 · Shared work, bounded access

Connect the tracker.

Linear holds projects, issues, statuses, and blocking relationships. Model Context Protocol connects Devin to the tools that the Linear server exposes. Tool discovery, authentication, read access, and write authorization are separate steps.

Core fallback

No Linear connection required

Review the same ticket drafts in chat or save them locally after approval. Keep local teaching IDs and a dependency list. Do not fabricate issue URLs or say anything was published.

Connected exercise

One selected team and project

Prefer a dedicated workshop project with known automation settings. Inspect its statuses and relevant existing issues read-only. Ask which server to use if multiple Linear connections appear.

Operator setup · Devin CLI + official read-only endpoint

These are optional setup commands for the human, not actions performed by this page. First run devin mcp list; reuse an appropriate existing connection instead of overwriting it. If you choose to add a new connection, run from the intended project directory:

devin mcp add linear-workshop https://mcp.linear.app/mcp/readonly
devin mcp login linear-workshop
devin mcp list

The add command changes local configuration; login opens the OAuth authorization flow. Confirm the intended account and scopes in the browser. Never paste tokens into the lesson, chat, or a ticket. Current CLI defaults to .devin/mcp_config.local.json; global configuration belongs under ~/.config/devin/. Version and organization settings may differ.

This endpoint cannot publish. Linear's standard https://mcp.linear.app/mcp endpoint supports writes with suitable authorization. Adding a write-capable connection is a separate human decision, not an automatic fallback. A “please read only” prompt is not equivalent to a read-only credential.

After setup, ask Devin to discover the current tools and schemas. A listed server is not proof of successful authentication. If authentication, permission, or organization policy blocks access, ask the operator; continue with local drafts rather than bypassing controls.

MCP is not the native Devin–Linear integration. The workshop demonstrates tool calls from this agent to Linear. Publishing can still trigger existing workspace notifications or automation; check the project configuration with its owner before authorizing writes. No agent assignees, trigger labels, or “start work” transitions in this phase.

04 · Optional extension

Small PRs first. Stacks when useful.

A pull request proposes code for review. A stack organizes deliberately dependent PRs so each diff shows one layer. Ticket dependencies describe work; PR dependencies describe code. They do not have to map one-to-one.

Beginner default

Sequential, focused PRs

Finish and review one visitor-facing slice. Merge only when approved, then start the next from the updated main branch. This makes the review loop visible without teaching stack maintenance at the same time.

Optional dependent stack

One feature, two layers

main
  └─ PR A: schedule renders local talks
       └─ PR B: track filtering + empty states

PR A targets main. PR B targets A's branch. Each includes its own checks. Review the base layer before the dependent layer. This illustrates splitting one schedule ticket, not making every conference page depend on the previous page.

Devin native stacks · capabilities, review, and limits

Current Devin documentation describes native stacks for GitHub.com repositories only. An ordinary chain of branches is not automatically a native stack. Do not assume the local CLI or an unconfigured repository exposes the same cloud session workflow.

For the documented native workflow, a stack merge lands the selected PR and every open PR below it, atomically, bottom-up. Remaining PRs are retargeted automatically. It is not the regular single-PR merge flow: inspect the affected PR count, CI, required reviews, conflicts, and branch protections first.

Say: “Propose a two-PR stack for the schedule feature. Explain each layer's diff, tests, dependency, and merge effect. Do not create branches, push, open PRs, rewrite history, or merge.”

Stop: diagram and review only. Any real push, PR creation, restack that rewrites history, or merge needs separate authorization. We are not creating a stack in this lesson.

# DesignCraft — Illustrative implementation plan

## Entry blockers and candidate architecture

- Real planning requires the participant's approved SPEC.md, actual reviewed DESIGN.md, shared assets, specimen, landing prototype, and review evidence. The Phase 3 example explicitly says these artifacts were not generated. Missing actual specimen/assets blocks a real build; this document cannot clear that gate.
- Inspect the separately authorized conference project directory, not `website/` or lesson folders. No application directory or stack has been selected here.
- Candidate A: plain HTML, shared CSS foundations, and minimal local JavaScript. Four clean routes `/`, `/schedule`, `/speakers`, `/rsvp`; native links; host-compatible page routing and unknown-path handling. Low infrastructure, but shared markup and clean-URL serving need deliberate handling.
- Candidate B: reuse an existing Vite setup only if inspection finds one and it is justified. Shared templates/components may help; a client router needs host fallback rules and explicit unknown-path rendering. Do not introduce Vite/React just because the workshop reference site uses React.
- All technology remains proposed. Human architecture approval must select the smallest viable option after inspection and resolve the hosting approach. Opening lesson HTML directly is not proof that conference clean URLs work.
- Proposed data: fixed event values, six speakers keyed by ID, eight talks referencing speakers; start-time then room ordering. Local filter state resets on reload. RSVP entries live only in page memory, with no transmission, persistence, analytics payloads, or console logging.
- Reuse actual reviewed tokens/patterns; propose missing form/filter patterns for design review rather than silently inventing an expanded library. Keyboard/focus, labels/status feedback, contrast, and 1440px/375px layout checks belong to every slice.
- **Schedule readiness blocker:** `../skills/index.html` demonstrates the unresolved I2 precedence question: when Product is selected and the whole dataset is empty, which message wins? “Schedule coming soon” taking precedence is an example recommendation, not approval. Ask the human, record the decision and aligned AC4 wording in the actual approved spec before T2 is ready. The example SPEC.md's “no blockers” claim does not resolve this ambiguity.

## Dependency graph and PR policy

Behavior DAG: T1 → T2, T3, T4; T2 + T3 + T4 → T5. T2 also depends on the human precedence decision. All tickets depend on entry artifacts and architecture approval; none is currently implementation-ready.

Default review/merge order: T1 → T2 → T3 → T4 → T5, ordinary sequential PRs against main after each predecessor merges. This is a review order, not invented data dependencies. Optional stacked-PR demonstration requires separate approval and supported tooling; no branches or PRs are created in this phase.

## T1 — Understand the event and enter the site

- Goal / requirements: R1, R5, D3; AC2 plus initial AC1, AC8, AC9, AC10 groundwork.
- Acceptance: runnable landing with approved fictional event details and notice; CTA targets `/rsvp`; shared navigation identifies all four destinations. Temporary destination shells explicitly identify unfinished pages, without claiming their behaviors work. Unknown paths show “Page not found” and a working home link.
- Shared-data ownership: T1 establishes one canonical local fixture source for event values, six speakers, and eight talks with valid speaker references; T2 and T3 consume it rather than copying data. Include fixture integrity checks in T1; feature empty-state tests use temporary inputs without changing the canonical source.

- Dependencies: entry gate and approved route/hosting approach. PR slice: one runnable landing plus shared shell and routing foundation.
- Exclusions: no completed schedule, speaker listing, RSVP, deployment, or claims that all-route AC1 passes. Any starter setup must be specifically authorized in Phase 5.

## T2 — Browse and filter the schedule

- Goal / requirements: R2, I1–I2, D4–D5; AC3, schedule portion of AC4, schedule references in AC5, AC8–AC9.
- Acceptance: eight talks, four per track, ordered 09:00/10:00/11:00/13:00 then room; time/title/speaker/track/room shown. All/Product/Engineering update without reload, expose selected state, reset to All on reload, and hide empty groups. Exact empty messages follow the human-approved precedence decision.
- Check plan: count/order all filters, resolve every speaker ID, use temporary no-match and wholly empty fixtures including Product selected, then restore normal fixtures. Keyboard/selected-state checks, both widths, direct entry/reload, console inspection, relevant available automated checks.
- Dependencies: T1 and unresolved precedence decision; blocked until both satisfied. PR slice: complete schedule visitor flow including fixtures, state, rendering, and checks.
- Exclusions: no new production filter, live feed, search, editing, personalized schedule, or silent adoption of the teaching answer.

## T3 — Learn about the speakers

- Goal / requirements: R3, I2, D4; AC5, speaker portion of AC4, AC8–AC9.
- Acceptance: all six fictional speakers show matching name, role, initials, and bio; empty data shows “Speakers coming soon.” Schedule references resolve to the same speaker identities, without requiring detail routes.
- Check plan: compare fixtures to approved content, inspect reference integrity, temporarily empty/restore speaker data, keyboard navigation, both widths, direct entry/reload, console and relevant available automated checks.
- Dependencies: T1; integration with T2 is rechecked in T5. PR slice: complete speaker browsing and empty state.
- Exclusions: no photos, profiles/detail pages, speaker management, or remote data service.

## T4 — Try the local-only demo RSVP

- Goal / requirements: R4, I3–I7, D2; AC6–AC7, AC8–AC9.
- Acceptance: initially empty labeled name/email fields; disclosure “Demo only. Use fictional details. Nothing is sent or saved.” and “Try demo RSVP” control. Trim outer whitespace; require nonempty name and browser-valid email. Invalid submission retains entries, associates “Enter your name.” / “Enter a valid email address.” errors, focuses first invalid input, and blocks success; revalidate on next submit.
- Acceptance: valid fictional input announces “Demo complete. No registration was sent or saved.”, clears fields/errors, and leaves form reusable. Typing removes stale success. Entries never leave page memory: no form request, storage, entry logging, or analytics transmission.
- Check plan: blanks, whitespace, malformed email, correction/resubmission, success/repeat/typing/reset; inspect network, console, storage, labels, error associations, status announcement, focus, both widths, and direct entry/reload. Run relevant checks only once actual tooling is known.
- Dependencies: T1 and reviewed form patterns. PR slice: complete local demo interaction with privacy verification.

## T5 — Complete and verify the cross-route journey

- Goal / requirements: R1–R5, I1–I7; final AC1–AC10 integration ownership.
- Acceptance: landing → schedule → speakers → demo RSVP works; no unfinished shells remain. All four native routes work by direct URL and reload under the selected host's actual or equivalent documented serving rules; unknown paths retain the required fallback. Deployment is not authorized by this verification requirement.
- Acceptance: consistent reviewed foundations, no horizontal overflow at 1440px/375px, keyboard-reachable controls and visible focus, associated errors/announced success, no new console errors. AC10 reports real discovered build/lint/test commands, results, and absent tooling honestly.
- Check plan: rerun each feature's checks and temporary fixtures, restoring normal data; capture both widths and relevant filter/form states. Verify hosting rewrites or directory routing rather than relying on client navigation alone. If target hosting is undecided or unavailable, mark route-host verification blocked, not passed. Review diff and report passed/failed/not-run with evidence.
- Dependencies: T2, T3, T4. PR slice: cross-route integration fixes and verification handoff, not a deferred dumping ground for all feature tests.
- Exclusions: no scope additions, production deployment, real personal data, fabricated command results, or automatic issue completion/agent launch.
