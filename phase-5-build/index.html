Phase 05 · Build + review

Build one slice.
Review the evidence.

Give a fresh session a reliable starting point. Implement one approved ticket, inspect what changed, and keep the documents honest.

  • BringApproved inputs + actual assets
  • PracticeHandoff → intake → one ticket
  • InspectTests, browser, diff, document drift
  • OptionalCloud handoff + stacked PRs
  • Leave withEvidence or explicit blockers

A summary is not a source of approval.

Start the practice →Understand context →

Choose real work or a dry rehearsal. Teaching documents are illustrative and unapproved; actual conference assets were not generated. Missing real inputs means chat-only practice, not permission to invent them. Reading this lesson or checking boxes changes no code or tracker.

01 · Say / do / decide

A small, repeatable loop.

Core path: reviewed handoff → fresh read-only intake → explicit one-ticket build → evidence review → separately authorized correction → document proposals. Dry rehearsal stops before execution.

01 / Choose the project, not just a conversation

Say: “We are building one approved slice, not everything ever mentioned.”

Do: locate actual approved spec, design, assets, specimen/prototype, architecture, ticket and application directory. Record versions and approval evidence. website/ is the workshop reference, not the conference app.

Decide: real approved inputs, or fictional chat-only rehearsal with the candidate T1 plan? T1 is landing, shared navigation, explicit destination shells, fallback and canonical fixtures—not completed destination features. Stop: missing real assets blocks a real build; it does not block learning.

02 / Prepare a handoff the next session can question

Say: “The next agent needs evidence, not confidence.”

Do: inspect /context; consider compaction or a fresh session. Authorize a bounded read scope. Paste: Prompt 1 in the current session. For a dry rehearsal, discuss the illustrative handoff without tools.

Expect: actual references/statuses, current revision and tracked/untracked work, scope, results, blockers and permission ledger. Check: challenge unsupported “approved”, “clean” or “passed” claims. Review sensitive material privately.

Decide: approve handoff contents for the recipient; save/share only by a separately agreed action. This does not authorize a build or cloud launch.

03 / Start fresh; catch the stale claim

Say: “Read the sources before trusting the summary.”

Do: open a fresh local session in the intended project; supply the reviewed handoff and accessible references. Paste: Prompt 2 with read-only scope. In rehearsal, discuss the expected reply instead of running tools.

Expect: goal, AC, exclusions, actual revision/changes, contradictions and setup/access gaps. Check: try the fictional stale-claim drill. The receiver should challenge it, not implement it.

Stop: review findings and missing approvals before execution. Cloud handoff is a separate optional launch decision.

04 / Authorize one ticket; inspect the result

Say: “Permission names a ticket, directory, approved version and command boundary.”

Decide: authorize exact setup/verification commands and allowed generated outputs, then enter execution mode. Paste: Prompt 3 only after approval. The rehearsal predicts evidence and stops before execution.

Expect: reuse of approved assets; a relevant failing test first where infrastructure exists; scoped implementation; real results. Missing test infrastructure is a gap, not permission to install it. Preserve unrelated tracked and untracked work.

Check: test output, browser states at 1440px/375px, keyboard/focus, console, relevant routes/reload, and diff against AC. Name revision, working-tree state and environment. T1 is not an all-route AC1 pass.

Stop: before scope additions, unapproved setup/config/install, Git mutations, PRs, tracker writes, cloud launches or deployment. No personal data or RSVP requests/persistence.

05 / Review first; authorize corrections separately

Say: “Can someone reproduce this finding?” Paste: Prompt 4 with the actual diff range and evidence.

Expect: prioritized criterion, actual versus expected, reproduction and evidence. Review is read-only; only explicitly agreed non-mutating commands. Tests writing caches, snapshots or reports need separate permission. Inspect only an approved browser target and interactions.

Check: an illustrative finding: “At 375px the landing CTA overflows; AC8 expects no horizontal scrolling. Reproduce with the long approved label.” This is an example, not observed evidence.

Decide: authorize a specific correction separately, then recheck affected states and diff. Optional Devin Review assists only if configured; it is not approval. Stop: no automatic fix, posted review, merge or issue completion.

06 / Reconcile sources, not just chat history

Say: “Which source is wrong, and who approved the change?” Paste: Prompt 5.

Expect: chat-only proposals distinguishing defects, already-approved decisions needing propagation, and new decisions. Check: affected source and derivative documents/ticket, exact wording, status, evidence timestamp, revision and downstream rechecks.

Decide: authorize exact document updates and targets only if wanted; inspect their diff afterward. Never rewrite a spec just to fit code. Stop: otherwise leave proposals in chat. MCP status updates need separate target/write approval.

07 / Optional: package the reviewed slice as a normal PR

Say: “A pull request is a review request, not proof that a task is complete.”

Do: request a proposed title/body in chat with the ticket, repository, base/head branches, diff summary, tests, browser evidence and limitations. Verify it contains only the approved slice and reviewed document updates.

Decide: separately authorize exact commit/branch/push and draft-PR actions and target if publication is wanted; keep merge and deployment excluded. Without repository access, finish with a local diff review.

Check: inspect the actual returned PR link, base/head, diff, CI and review status. Required checks and branch protections still apply. Stop: no automatic merge or issue completion. Propose the exact evidence-backed tracker update for its own approval.

A useful finish

“Blocked” can be correct.

The example design handoff does not contain generated assets. A fresh agent noticing that gap has improved the handoff—not failed the exercise.

Evidence over narrative

Passed on which revision?

A test result without its command, environment and revision is hard to reuse. A screenshot of yesterday’s preview is not today’s browser verification.

One bounded change

Do not grow the ticket.

Fixing a reviewed T1 finding does not authorize schedule filters, RSVP or deployment. Record the next decision instead of guessing it.

02 · Context is finite

Keep the right things in view.

Tokens are units of model input/output, often parts of words. Instructions, conversation, attached material, retrieved files and tool results share a finite context window. Retrieve relevant sources rather than paste everything.

Context rot

Informal shorthand for reliability problems when long, noisy or conflicting context obscures the task. Not an inevitable failure at a fixed threshold. A fresh session helps only if it can inspect the sources and boundaries.

Content rot ≠ document rot

Content rot is stale visitor-facing or teaching copy. Document rot is drift among decisions, spec, design, plan, tickets and implementation. Shortening the conversation fixes neither by itself.

Mini feature map · use the smallest useful tool
  • /context inspects usage; /compact reduces context through a lossy summary—not fact checking or approval.
  • /handoff launches remote work and transfers context; it needs a separate human decision.
  • Scoped edits + terminal checks implement one approved ticket with real commands and output boundaries.
  • Browser + diff review compare observed behavior and changes at a known revision. Optional Devin Review is configured assistance, not approval.
  • MCP status updates require separately approved targets and writes; native Linear delegation is distinct.

See the CLI command reference and skills companion. No new skill or configuration is required.

03 · Local first

Transfer references and limits.

Prepare in the current session, review contents, then open a fresh local session with the handoff and accessible sources. Ask for read-only intake—not “continue building.”

What a receiver must verify

Actual source versions and approval records; repository, branch, current commit and tracked/untracked changes; exact ticket/AC; assets; setup commands and environment; check results with timestamp/revision; blockers; permission ledger and next stop. Preserve other work. An approval claim in the summary must point to actual evidence.

The 45-line illustrative T1 handoff deliberately contains unknowns and NOT RUN checks. It invents no branch, commit, issue link, passing test or approved asset. A real handoff replaces unknowns with inspected facts and links; it does not erase blockers to look ready.

04 · Optional facilitator demo

A remote session is a new boundary.

Cloud is not required. A launch may consume credits and transmit context and work. First approve the account, repository, data transfer, cost and READ-ONLY intake scope—not implementation.

Built-in CLI /handoff · how to demonstrate it safely

The current built-in command needs no plugin. Human confirms organization/account, repository, recipient/session scope, accessible inputs, transfer and cost. Privately inspect tracked and untracked work using supported controls; never paste credentials. If private changes cannot safely be excluded, stop and resolve with the operator. Do not commit secrets or broadly stash work as a workaround.

The handoff documentation describes conversation, repository/branch and uncommitted diff transfer; the CLI changelog notes untracked-file collection across the repository too. Inspect what transfers. Do not promise the whole environment, ignored files, credentials, MCP configuration or local server carries over.

Only after explicit launch authorization, replace the reference and invoke in the CLI:

/handoff Read the reviewed handoff at [accessible reference]. Verify repository, branch, transferred changes, ticket, and setup/access gaps. Report findings and stop before implementation.

Do not run this because the lesson shows it. Avoid bare /handoff: without arguments it can automatically continue the task. Record an actual session link only after a successful authorized launch. In the received session, use Prompt 2 to verify revision, received tracked/untracked work, inputs, approvals and setup/access gaps. Stop before implementation.

Manual delegation and receiving remote work back

Manual cloud delegation is a separate path: deliberately provide an accessible repository revision and artifacts after account/access/cost approval. Uncommitted laptop files are not automatically available without transfer. Verify received state; do not assume local setup or integrations exist remotely.

For either route, prevent concurrent local/remote edits to the same ticket/branch. Revalidate returned PRs and evidence against the current revision before local use. A remote PR does not synchronize your laptop. No blind cherry-pick or merge.

Native Linear integration can delegate when configured; MCP exposes scoped tools. They are distinct. Creating an issue does not itself authorize an agent to start; inspect existing automation before approved tracker writes.

05 · A practical dry drill

Catch one stale sentence.

A handoff can be tidy and wrong. Use this deliberately fictional claim to practice contradicting a summary with a source—not changing the source to match the summary.

Deliberately stale handoff line

“RSVP sends confirmation email”

Discuss in chat only. No repository edits, network calls, personal data or tracker changes. RSVP implementation is outside candidate T1.

Expected intake catch

D2 / I6 say demo-only.

Compare the example spec: no sending and no persistence. Propose: “RSVP is demo-only; nothing is sent or saved.” Flag the conflict and request review. The teaching decision is not real project approval.

Give each source a job · avoid duplicate truth
  • SPEC.md: intended product behavior and exclusions.
  • Design sources + DESIGN.md: visual decisions, reusable assets and limitations.
  • Plan + Linear ticket: current slice, dependencies and acceptance-criteria references.
  • Code + verification evidence: actual implementation and observations, not automatic product approval.
  • AGENTS.md: stable conventions and verified commands, not every temporary status.
  • Session handoff: current work, evidence references, blockers and the next bounded action.

Link instead of copying whole documents into every ticket. Identify the owner/source, version and status; review affected references when decisions change. Preserve historical results under their original revision rather than relabeling them as current. Neither code nor documentation is automatically right when they disagree.

After implementation · reconcile without erasing disagreement

With Prompt 5, identify the governing decision, actual behavior and every affected source/derivative: spec, design, plan, ticket, handoff or visitor copy. Propose exact wording with status, timestamp, revision and evidence. If behavior is wrong, propose a code correction; if a decision changed, require its approval record. Ask which source governs if authorities conflict.

Authorize exact updates only if wanted, then inspect the diff and downstream references. A shorter chat is not document maintenance. A stale sentence shown to visitors is content rot; a conflicting ticket is document rot too.

06 · Optional, after the core loop

Stack only when it helps review.

Default to one ordinary PR for one slice. Use Prompt 6 for a read-only proposal—not permission to create branches, PRs or merges.

One schedule ticket, two dependent review layers
main -> PR A: render schedule -> PR B: filter and empty states

A owns base rendering and tests using T1's canonical fixtures. B adds filter/empty-state tests and checks final combined behavior. Neither layer duplicates the shared fixture source. Resolve I2 empty-state precedence first. A lower-layer change requires an upper-layer recheck.

Native Devin stacks are first-class GitHub.com stacks, not an ordinary dependent branch chain or a feature guaranteed in every CLI/repository. Native merge includes the selected layer and all open layers below atomically, then auto-retargets remaining layers. Regular merge is not that native operation. Verify support; use sequential ordinary PRs otherwise. This lesson creates or merges no PRs.

07 · Copy only what you need

Six bounded prompts.

Replace placeholders with reviewed, accessible references. Prompts do not grant themselves permission. Download all six; facilitator script. For rehearsal, discuss the prompts in chat without execution.

1 / Prepare the handoff · current session, chat only
Prepare a fresh-session handoff in chat only for [exact ticket] in [authorized project directory]. Inspect only [authorized inputs and repository]. Reference [authoritative spec, design, assets, plan and ticket versions] rather than duplicating their full contents. Identify their actual approval statuses and supporting references; distinguish inspected facts, proposals, and explicit human approvals. A summary is not approval.

Record the repository, current branch and commit, tracked modifications and untracked work, without exposing secrets or changing Git state. Identify other people's work to preserve. State the candidate scope, exclusions, acceptance criteria references, blockers, and permission ledger. For each check, give the actual result, command, revision, environment and evidence timestamp; use NOT RUN or unknown where appropriate. Do not invent passing tests, assets, issue IDs, or a clean tree.

Name the next permitted action as read-only intake and its stop condition. Flag stale or conflicting claims for human review. Do not edit files, mutate Git, launch cloud work, or update a tracker. Stop for review of the handoff contents.

2 / Fresh-session intake · verify, then stop
Perform read-only intake for [exact ticket] using [reviewed handoff reference] in [local session or already-authorized cloud session]. Inspect only [authorized repository/directory and source references]. Verify the actual repository, branch, current commit, tracked changes and untracked work against the handoff; report absent or additional work. Reopen the authoritative spec, design, assets, plan and ticket at [approved versions], checking actual statuses and approval evidence rather than trusting the summary.

Recite the goal, acceptance criteria, exclusions, dependencies, blockers and permission ledger. Identify contradictions, stale claims, inaccessible artifacts, and any missing assets. Inspect documented setup and verification commands without executing them. For cloud intake, confirm the intended organization/account, repository access, received changes, and required integrations without exposing secrets; do not assume local environment or MCP connections transferred.

Report what is known, unknown, and required before a build. Do not edit files, run tests or setup, install anything, change configuration, mutate Git, call tracker writes, or launch another session. Stop and ask for explicit one-ticket execution authorization.

3 / One-ticket build · explicit execution permission required
I authorize implementation of [exact ticket] only in [directory], using [approved version of spec, design, assets, plan and ticket]. The permitted setup commands are [permitted setup commands, or none]; the approved verification commands are [exact commands and allowed generated outputs]. Confirm these boundaries against the reviewed intake before editing. Stop if required inputs or approvals are missing.

Reuse the actual approved assets and existing project patterns. Discover real commands from the project, not guessed scripts. Where test infrastructure exists, add or adjust a relevant test and demonstrate its expected failure before implementation; otherwise report the gap without installing a framework. Implement only this ticket's acceptance criteria, preserving unrelated tracked and untracked work. Use fictional data only; no personal data or RSVP network requests or persistence.

Run authorized checks, inspect relevant states at 1440px and 375px, keyboard behavior and console errors, then review the diff. Report evidence, revision and environment, including failures and NOT RUN checks. Stop before scope additions, unapproved setup/configuration/install, commits, branches, pushes, PRs, cloud launches, tracker writes or deployment.
Not for the dry rehearsal

4 / Review · findings, not automatic fixes
Review [exact ticket] read-only in [authorized directory] against [approved acceptance criteria, spec and design versions]. Inspect [base revision] to [current revision plus identified working-tree changes], preserving other work. Compare the actual diff with the approved scope and exclusions. Review [test output and browser evidence references] for the same revision and environment; distinguish observations from unverified claims.

Use only [explicitly agreed non-mutating check commands, or none]. Do not rerun tests that create files, caches or snapshots under this permission. If more execution or evidence is needed, propose it and stop for separate authorization. Inspect [approved browser target] only within its agreed local, fictional-data interactions; do not assume a remote preview matches this revision.

Give prioritized, actionable feedback: criterion, file or state, actual versus expected behavior, reproduction steps, and supporting evidence. Include responsive, keyboard, privacy and console findings where relevant. Mark gaps NOT VERIFIED, never fabricate a pass or merge approval. Do not edit files, fix findings, mutate Git, publish review comments, or update tickets. Stop with recommendations for a separately authorized correction.
Approve corrections separately

5 / Reconcile documents · propose exact changes in chat
Compare [authoritative decision/spec references and approved versions] with [design/assets references], [plan and exact ticket], and [implementation revision plus identified working-tree changes]. Use only [authorized read-only sources and evidence]. Propose document reconciliation in chat only; do not apply changes. Distinguish stale visitor or teaching content from disagreement between specification, design, tickets and implementation.

For each discrepancy, state the source requirement, actual implementation or claim, evidence, and affected source and derivative documents or ticket fields. Identify whether the implementation needs correction, an already-approved decision needs propagation, or a new product decision is required. Never silently rewrite the specification to fit the code or treat a summary as approval. If authoritative sources conflict, ask the human which decision governs.

Propose exact replacement wording with status, evidence timestamp, revision and environment where relevant. Preserve unknown, failed and NOT RUN statuses honestly. List downstream references to recheck and any remaining blockers. Request approval for the exact updates and targets before applying anything. No file, tracker, Git, configuration or cloud changes. Stop with the reconciliation proposal.
No silent spec rewrite

6 / Optional stack · a read-only proposal
Prepare a read-only proposal for [one approved schedule ticket] in [authorized repository] using [approved plan, design, acceptance criteria and current revision]. Default to one ordinary PR; explain whether two dependent review layers would genuinely help. Do not implement anything or create branches or PRs.

If useful, propose main -> PR A: render schedule -> PR B: filter and empty states. This is one ticket split across two PRs, not independent features. Map acceptance criteria, scope and tests to each layer; keep shared fixtures owned once. Explain how changes to the lower layer require rechecking the upper layer and how reviewers verify the final combined behavior. Identify unresolved empty-state precedence as a blocker if not approved.

Verify the proposed tooling: native Devin stacks are GitHub.com-only, not every CLI or repository, and not an ordinary dependent branch chain. Native merging includes the selected layer and all open layers below atomically, then retargets remaining layers; regular merge is different. Report access/support gaps, suggest a sequential fallback, and stop for human review. No Git mutations, remote actions, merges or tracker changes.
Default: one ordinary PR
