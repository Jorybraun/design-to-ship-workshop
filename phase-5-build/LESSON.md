# Phase 5 — Build one slice. Review the evidence.

## Outcome and entry gate

Practice a reliable change of session, then a bounded implementation and review loop. Leave with a reviewed handoff, one ticket's evidence or explicit blockers, and document-drift proposals. This is not a deployment lesson. Continue with [Phase 6 · Ship + handoff](../phase-6-ship/index.html) after reviewing the release prerequisites.

Bring the actual approved spec, design, reusable assets, specimen/prototype, architecture, ticket and authorized application directory. Record versions and approval evidence. `website/` is the workshop reference site, not the conference application. The Phase 2 spec, Phase 3 design and Phase 4 plan are illustrative and unapproved; actual design assets were not generated by those documents. If inputs are missing, choose the fictional chat-only rehearsal. It is valid to finish with blockers instead of code.

Open `index.html` directly; no build is needed. Reading this lesson, copying a prompt or completing its session-only checklist changes no code or tracker and grants no execution permission.

## Context before code

A token is a unit of model input/output, often part of a word. The context window is finite: instructions, conversation, attached material, retrieved files and tool results compete for space. Relevant retrieved context matters more than pasting the entire repository. Keep authoritative references discoverable and inspect them at the current revision.

“Context rot” is informal shorthand for reliability problems when long, noisy or conflicting context obscures the task. It is not an inevitable failure at a fixed threshold. “Content rot” is stale visitor-facing or teaching copy. “Document rot” is drift among decisions, spec, design, plan, tickets and implementation. A shorter chat does not repair either kind of stale content.

Use `/context` to inspect context usage in the current CLI. `/compact` makes a lossy summary to reduce context; it is not fact checking, source reconciliation or renewed approval. A fresh session also needs references and permission boundaries, not just a confident summary. See the [CLI command reference](https://docs.devin.ai/cli/reference/commands).

## Give each source a job

- Approved SPEC.md owns intended product behavior and exclusions.
- Design sources and DESIGN.md own visual decisions, reusable assets and known limitations.
- The plan and Linear ticket own the current slice, dependencies and acceptance criteria references.
- Code and verification evidence show actual implementation and observations, not automatic product approval.
- AGENTS.md holds stable project conventions and verified commands, not every temporary status or chat transcript.
- The session handoff records current work, evidence references, blockers and the next bounded action.

Link instead of copying whole documents into every ticket. Name the owner/source, version and status. When a decision changes, review affected references in the same change; retain historical evidence with its original revision rather than relabeling old results as current. When sources conflict, investigate and ask for the governing decision instead of declaring either code or documentation automatically correct.

## Facilitator walkthrough

### 1. Choose the real path or a dry rehearsal

- **Say:** “We are building one approved slice, not everything the conversation ever mentioned.”
- **Do:** locate actual inputs and approval records, or label the exercise fictional and chat-only. Read the candidate T1 in `../phase-4-plan/PLAN.md`: landing, shared navigation, explicit destination shells, fallback and canonical fixtures; not completed destination features.
- **Decide:** real build readiness or hypothetical rehearsal? Missing actual assets blocks the real path.
- **Stop:** no setup, edits or integrations merely to make the example look complete.

### 2. Prepare and review a handoff

- **Say:** “The next agent needs enough evidence to challenge this summary.”
- **Do:** inspect `/context`; discuss whether compaction or a new session would help. Use [Prompt 1](PROMPT.md) in the current session after authorizing its read scope. For the dry path, discuss `HANDOFF.md` without tools or project inspection.
- **Paste:** Prompt 1 with exact ticket, authorized inputs and directory filled in.
- **Expect:** references with actual status/version, repository revision and tracked/untracked changes, scope, evidence, blockers and permission ledger. Unknown stays unknown.
- **Check:** inspect handoff contents, especially unsupported “approved”, “clean” or “passed” claims. Review sensitive work privately; do not paste credentials.
- **Decide:** approve the handoff contents for the selected recipient. That is not authorization to implement or launch cloud work. Save/share only by a separately agreed action.

### 3. Start fresh and catch a stale claim

- **Say:** “Read the sources before trusting the handoff.”
- **Do:** open a fresh local session in the intended project, supply the reviewed handoff and accessible references, and authorize read-only intake. Cloud is an optional separate route below.
- **Paste:** Prompt 2. In the dry rehearsal, discuss its expected response rather than running tools.
- **Expect:** the new session recites goal, AC, exclusions, current revision, changes, missing setup/access and explicit stop boundary. It reports contradictions rather than fixing them.
- **Check — fictional dry drill:** present this deliberately stale handoff line: **“RSVP sends confirmation email”**. Compare it with example SPEC.md D2 and I6. They require demo-only behavior, no sending and no persistence. Expected response: flag the conflict and propose “RSVP is demo-only; nothing is sent or saved.” Do not alter the repository. The example is not an approved project decision, and RSVP implementation is outside candidate T1.
- **Stop:** review intake findings; resolve missing real inputs before any build.

### 4. Authorize exactly one ticket, then inspect evidence

- **Say:** “Permission names a ticket, directory, approved version and command boundary.”
- **Decide:** explicitly authorize the exact ticket and permitted setup/verification commands, including allowed generated outputs. Only then use execution mode. The dry rehearsal stops before execution and predicts evidence, not results.
- **Paste:** Prompt 3 only after that decision. Reuse actual approved assets and preserve unrelated tracked/untracked work. No personal data or RSVP requests/persistence.
- **Expect:** a relevant failing test first where infrastructure exists, scoped implementation, then actual check results. Missing infrastructure is a gap, not permission to install a framework. Discover real commands; do not invent scripts.
- **Check:** test output, relevant browser states at 1440px/375px, keyboard/focus, console, routes/reload where applicable, and the diff against AC. Evidence must name the revision, working-tree state and environment. T1 does not complete all-route AC1.
- **Stop:** before scope additions or unapproved setup/config/install, Git mutations, PRs, tracker writes, cloud launches or deployment.

### 5. Review, authorize corrections separately

- **Say:** “A review should let someone reproduce the problem.”
- **Paste:** Prompt 4 with the actual diff range and evidence. Review is read-only; only explicitly agreed non-mutating commands are allowed. Tests that write caches, snapshots or reports need separate permission. Use only an approved browser target and interactions.
- **Expect:** prioritized findings with criterion, actual versus expected, reproduction and evidence; unverified checks stay unverified. Example feedback: “At 375px, the landing CTA overflows; expected no horizontal scrolling under AC8. Reproduce at the supplied local URL with the long approved label.” This is an illustrative finding, not observed evidence.
- **Decide:** authorize a specific correction separately, then recheck the affected states and diff. Optional Devin Review is review assistance only if configured, not approval or a substitute for evidence.
- **Stop:** no automatic fixes, posted reviews, passing claims, merge or issue completion.

### 6. Reconcile the documents, not just the chat

- **Say:** “Which source is wrong, and who approved the change?”
- **Paste:** Prompt 5 for read-only drift analysis after review.
- **Expect:** exact proposals for affected authoritative sources and derivative design notes, plan, ticket or handoff. Separate implementation defects from already-approved decisions awaiting propagation and genuinely new decisions.
- **Check:** source/decision reference, actual behavior, affected documents, proposed wording, status, timestamp, revision and downstream rechecks. Stale visitor copy is content rot; a ticket claiming email against D2/I6 is document rot too.
- **Decide:** authorize exact document updates and targets only if wanted, then inspect their diff and references. Do not silently rewrite a spec to fit code. A tracker status update through MCP requires separate approval and evidence.
- **Stop:** otherwise leave the proposals in chat. A finished checklist records review, not permission.

### 7. Optional: package the reviewed slice as a normal PR

- **Say:** “A pull request is a review request, not proof that a task is complete.”
- **Do:** ask for a proposed title/body in chat with exact ticket, repository, base/head branches, diff summary, tests, browser evidence and limitations. Confirm the diff contains only the authorized slice and reviewed documentation updates.
- **Decide:** if publication is wanted, explicitly authorize the exact commit/branch/push and draft-PR actions and target. Keep merge and deployment excluded. The build prompt alone does not grant those actions. Without repository access, finish with a local diff review instead.
- **Check:** after authorized publication, inspect the actual returned PR link, base/head, diff, CI and review status. Required checks and branch protections still apply. A remote PR does not synchronize the local working tree.
- **Stop:** do not merge or mark the Linear ticket complete automatically. Propose the exact evidence-backed tracker update and obtain its own approval.

## Optional cloud facilitator demo — two distinct paths

### Built-in CLI handoff

The current built-in `/handoff` launches a remote session, may consume credits, and transmits context and work. It is not a plugin to install. The [handoff documentation](https://docs.devin.ai/cli/handoff) describes transfer of conversation, repository/branch and uncommitted diff; the [CLI changelog](https://docs.devin.ai/cli/changelog/stable) also notes collection of untracked files across the repository. Inspect the transfer scope, including tracked and untracked work; do not promise that the entire environment, ignored files, credentials, local server or MCP configuration travels with it.

Before invocation, the human confirms organization/account, repository, intended recipient/session scope, accessible approved inputs, data transfer and cost, and that the first remote task is READ-ONLY intake. Inspect sensitive material privately using supported controls; never paste credentials. If private changes cannot safely be excluded, stop and resolve with the operator. Do not commit secrets or broadly stash work as a workaround.

Only after those approvals, the facilitator may invoke this example in the CLI with a real accessible reference:

`/handoff Read the reviewed handoff at [accessible reference]. Verify repository, branch, transferred changes, ticket, and setup/access gaps. Report findings and stop before implementation.`

Do not run it simply because it appears here. Avoid bare `/handoff` in this workshop: without arguments it can automatically continue the task. Record the actual session link only after a successful authorized launch. In the received session, use Prompt 2 and verify repository, revision, received tracked/untracked work, approvals, setup/access and stop boundary. No automatic implementation.

### Manual cloud delegation

A separately authorized manual cloud session needs a deliberately supplied accessible repository revision and artifacts. Uncommitted laptop files are not automatically available without transfer. Verify account, access and costs before launch; then verify what arrived rather than assuming equivalence with local state. Do not have local and remote agents edit the same ticket/branch concurrently.

For either path, returned PRs and test evidence must be revalidated against the current revision before local use. A remote PR does not mean the laptop is synchronized. No blind cherry-pick or merge. Native Linear integration can delegate work when configured; MCP exposes tools for scoped reads/writes. They are distinct, and creating an issue does not itself authorize starting an agent. Check existing automation before approved tracker writes.

## Optional stacked-PR discussion

Default: one ordinary PR for one slice. Use Prompt 6 only for a read-only proposal when two dependent schedule review layers help:

`main -> PR A: render schedule -> PR B: filter and empty states`

This is one schedule ticket across two PRs. A owns base rendering and its tests using T1's canonical fixtures; B adds filter/empty-state tests and the final combined behavior. Neither layer duplicates the shared fixture source. Resolve the I2 empty-state precedence decision first. A lower-layer change requires an upper-layer recheck.

[Native Devin stacks](https://docs.devin.ai/work-with-devin/stacked-prs) are first-class GitHub.com stacks, not ordinary dependent branch chains or a capability guaranteed in every CLI/repository. Native merge includes the selected layer and all open layers below atomically, then auto-retargets remaining layers. Regular merge is not that native operation. Verify configured support; fall back to sequential ordinary PRs. This lesson creates or merges no PRs.

## Small feature map

- `/context`: inspect usage; `/compact`: reduce context with a lossy summary; `/handoff`: separately authorized remote launch and transfer.
- Scoped edits and terminal checks: one approved ticket, real discovered commands, explicit setup/output boundaries.
- Browser and diff review: observed behavior plus changes at a known revision, not a confident completion message.
- Optional Devin Review: configured review assistance, not human approval.
- MCP status update: separate exact target/write approval after evidence review; not implied by a checklist or native Linear integration.
- [Skills companion](../skills/index.html): methods to improve questions and review; no skill/config installation is needed here.
