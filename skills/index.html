01 · What a skill contributes

Package the process.

A skill bundles reusable instructions and may include supporting files or scripts. The agent reads that guidance in context. It is not a new model, a credential, or a guarantee of a correct result.

Perspective only
Act as a senior product manager.
Review my specification.
  • Suggests a viewpoint
  • Doesn’t specify what to inspect
  • Doesn’t define decisions, outputs, or stopping rules
An explicit method
Compare the specification with the reviewed brief.
Find a consequential ambiguity.
Ask me to decide; propose replacement wording.
Stop before editing or implementation.
  • Names the inputs and checks
  • Separates facts from human decisions
  • Defines the output and permission boundary
Say to the room

First a prompt, then a reusable method.

“If the same review instructions help us repeatedly, we can package them as a skill. We still provide this project’s context, and we still approve the result.”

Three different things

A prompt is the current request. A skill is a reusable method. MCP is a standard for connecting to exposed tools and context. A skill may instruct the agent to use MCP tools; it does not provide their credentials or permissions.

Inside a skill

Read the instructions, not just the name.

Look for inputs, steps, dependencies, outputs, side effects, and stop conditions. Inspect scripts and referenced files too. A short wrapper can call a much more capable skill.

Our local example

design-system-foundations is our workshop-authored skill, not one of Matt’s. It proposes a minimal inventory, waits for approval, creates authorized assets and a specimen, then stops for review.

02 · Matt Pocock’s examples

Small skills. Different jobs.

Matt describes his collection as small, adaptable, and composable. These summaries are based on the linked source files at a pinned revision—not an installation guide or a claim that every skill fits this workshop unchanged.

Interview · Phases 1–2

grill-me → grilling

grill-me is a user-invoked wrapper that calls grilling. The underlying method explores a decision tree and asks rounds of questions whose prerequisites are settled, recommending an answer for each.

Important difference: the current method can ask several independent questions in one round. It is not our workshop’s one-question-at-a-time adaptation. It delegates fact-finding and waits for the user’s decisions and final confirmation.

Read the grilling method →
Interview + documentation · Optional

grill-with-docs

Calls both grilling and domain-modeling. Its declared purpose includes sharpening shared terminology and creating domain/decision documentation as the conversation proceeds.

Inspect before use: this is not simply a read-only critique. Review the dependency instructions and authorized documentation locations before using it in a live repo.

Read the wrapper and follow its dependencies →
Synthesize · Phase 2

to-spec

Turns the current conversation and codebase understanding into a specification. It explicitly avoids a new discovery interview, although it asks the user to confirm proposed testing seams.

Side effect: it publishes to the configured issue tracker and applies a ready-for-agent label. Our lesson instead presents a draft and waits for approval before saving or publishing. These are different behaviors.

Read to-spec →
Explore a question · Phase 3

prototype

Uses a throwaway prototype to answer a question. Its logic branch produces a single shareable HTML file; its UI branch explores several different visual alternatives. Each branch has a supporting instruction file.

Different purpose: upstream deliberately skips tests and abstraction for disposable exploration. Our design-system exercise preserves reusable foundations and verifies them. Do not confuse a throwaway experiment with the system you plan to keep.

Read prototype and its branch references →
Plan deliverable slices · Phase 4

to-tickets

Breaks a plan into small, end-to-end tickets with explicit blockers. A slice should demonstrate a behavior, rather than only finish a technical layer. It asks the user to review granularity and dependencies before publishing.

Example: “Filter talks by track, including empty results and checks,” rather than separate unconnected tickets for a button, data function, and test. Upstream supports configured local files or a real tracker.

Read to-tickets →
Existing codebase review · Later

improve-codebase-architecture

Inspects an existing codebase for architectural friction, presents candidates in an HTML report, and interviews the user about the selected candidate using supporting design/domain skills.

Not a generic new-project planner: it has codebase and documentation expectations, writes a report, and can update domain documentation. For our beginner build, introduce only when there is actual code and a concrete design problem.

Read improve-codebase-architecture →

Two workflows, not one attribution. Matt’s tools can support interview → spec synthesis → tickets. Our teaching loop is draft → challenge → revise → explicitly approve, with slower questioning and no automatic tracker publication. Those guardrails are our adaptation.

03 · A worked workshop example

Grill one decision.

Use the DesignCraft spec as a teaching example. The schedule has two empty messages but does not define which takes precedence. We can resolve that without implementing anything.

01 / Say why we are reviewing
Say

“A polished spec can still hide decisions. We’ll challenge one ambiguity, decide what we mean, and turn the answer into clearer wording.”

Open the example specification and find I2. For a real project, use the actual reviewed brief and draft.

02 / Ask a consequential question
Example agent question
If the entire schedule is empty while Product is selected, should visitors see “Schedule coming soon” or “No talks in this track yet”?

I recommend checking for an empty dataset first. The track message is useful only when talks exist but none match. Is that the intended behavior?

This asks for a product decision. The agent should look up existing behavior where it can, not ask the participant to discover facts already in the repo.

03 / Decide, then revise
Your example answer
Yes. Show “Schedule coming soon” when there are no talks at all. Only use the track-specific message if other talks exist.
Proposed wording
Check the whole dataset first:
- No talks → “Schedule coming soon.”
- Talks exist but none match the selected track → “No talks in this track yet.”

Ask the agent to include the same precedence in the acceptance criteria. Review the proposed change before applying it.

04 / Stop without pretending the spec is perfect
Check

The ambiguity is resolved, the decision is recorded, and related requirements agree. Continue with another consequential issue, or pause with an explicit list of blockers. The reviewer’s confidence is not human approval or evidence that the application works.

Matt’s method

Ask what can be decided now.

His current grilling method explores independent questions in rounds. Dependent questions wait until their prerequisites are settled.

Our teaching adaptation

One question, one visible change.

We slow the process down so the room can follow the reasoning. We add explicit boundaries: no writes, no implementation, and a review record before approval.

Expected output

A decision, not more ceremony.

“Empty dataset takes precedence” plus replacement wording, the affected acceptance criterion, and any remaining blockers.

Use a structured interview to challenge this draft specification.
This is a workshop adaptation, not a verbatim Matt Pocock skill.

Reviewed brief: [paste or attach the brief].
Draft specification: [paste or attach the draft].

Read the references first. If either is missing, ask for it. Look up facts available in the supplied project context rather than asking me to find them.

Find the most consequential ambiguity, contradiction, unsupported assumption, or unnecessary scope. Cite the requirement. Ask one focused question at a time, explain why it matters, and recommend an option without deciding for me. Do not ask questions the documents already answer.

After I confirm a decision, propose precise replacement wording and identify related acceptance criteria that need to change. Keep a short record of confirmed decisions and remaining blockers. Do not edit files, publish issues, or implement anything.

Stop when no identified blockers remain or when I pause the review. Request explicit human approval of the revised draft; do not claim the review proves it is flawless.

04 · Before installing or adapting

Read the fine print.

A skill is instructions that may direct real actions. Read the full method and dependencies. Do not install a collection just because the first command sounds useful.

Inspect
  • Who wrote it, which revision, and what license applies?
  • Does it invoke other skills, scripts, or referenced instructions?
  • Will it write files, publish issues, run code, commit, or access a service?
  • Does it stop before the action you want to approve?
  • What inputs and project configuration does it expect?
For Matt’s engineering collection

setup-matt-pocock-skills configures tracker and documentation conventions used by other engineering skills. It can update repository instructions and create configuration documents. Inspect that workflow too; do not run setup as an invisible prerequisite.

Read the setup skill →
Adapt deliberately

Matt’s source uses fields such as disable-model-invocation. Our Devin project uses documented triggers: [user] for user-only skills. Host support, skill discovery, tool names, and permission handling vary; do not assume a copied header enforces the same behavior everywhere.

Keep the original distinct

Pin the reviewed version and label your changes. The inspected repository uses the MIT license; retain the required notice when copying substantial material. This chapter paraphrases the methods and links to the original files.

For this workshop

Start with the copyable review exercise. If adopting upstream skills later, select and inspect their full dependency set, confirm host compatibility and write scope, then install intentionally. No upstream skills have been installed by this chapter.
