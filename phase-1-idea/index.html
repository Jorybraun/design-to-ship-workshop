Phase 01 · Product discovery

Decide what.
Then build.

Turn a vague website idea into a clear brief. You make the product decisions. The agent helps you ask the right questions.

  • Starting point“A design conference website”
  • Your roleDecide audience, purpose, scope
  • Agent’s roleInterview, clarify, summarize
  • OutcomeOne agreed idea brief

Don’t delegate your product decisions by accident.

01 · The starting point

A request is not yet a brief.

Before choosing technology or designing pages, decide who this is for and what they need to accomplish. A vague instruction leaves those decisions open.

Too much left to guess
Build me a website for a design conference.
  • Who is the conference for?
  • What should visitors do?
  • Does registration involve payments or accounts?
  • What are we explicitly not building?
A better first move
Help me clarify the idea before we build anything. Ask one product question at a time. I’ll make the decisions; you organize them into a brief.
  • Discovery, not implementation
  • Human decisions, agent-assisted questions
  • One concrete artifact at the end
  • A clear stopping point before specification

If the agent starts choosing frameworks, inventing event details, designing pages, or writing code, bring it back to discovery.

Audience. Purpose. Boundaries.

Who is this for? What is the one job the site must do? What are we deliberately leaving out?

The agent helps

Questions, not assumptions.

It interviews you, organizes your answers, and identifies what is still undecided. It does not silently fill in missing product decisions.

Facilitator notes · How to explain this to the room
“Our first instinct may be to ask the agent to build a conference website. That delegates product decisions, not just implementation. Before opening the coding loop, we decide who the site serves, the one job it performs, and what we are not building. We can use the agent as an interviewer, but it should expose decisions rather than silently make them.”
03 · The discovery prompt

Brief the interviewer.

Copy this into your agent, then answer its questions. The output is a brief in the conversation—not a built website. Expand the notes to understand why each instruction is there.

Context:
I am defining a small website project for a hands-on workshop. The project must be focused enough to design, build, verify, and review during the workshop.

Initial idea:
A website for a one-day product design conference.

Task:
Help me clarify this idea before we write a specification, choose technology, design the interface, or build anything.

Method:
Ask me one focused question at a time. Help me decide:
- who the primary audience is,
- what single job the website should perform,
- what the visitor's main journey is,
- which capabilities are essential,
- what should be explicitly out of scope,
- and which product decisions remain unresolved.

When an answer is vague, ask a concrete follow-up question. Present a small set of meaningful options when that would make the decision easier. Do not answer product questions on my behalf.

Constraints:
Do not propose a technology stack, visual style, page structure, data model, or implementation plan yet. Do not create or modify files. Keep the project small enough for a workshop exercise.

Verification:
Before finishing, check that the result names a specific audience, one primary job, a coherent visitor journey, clear scope boundaries, and all unresolved decisions. If any item is missing, ask another question.

Deliverable:
After I answer the questions, produce a concise idea brief with these headings:
- Description
- Audience
- Primary job
- Main user journey
- In scope
- Out of scope
- Unresolved decisions

Stop after presenting the brief. Do not proceed to specification or implementation.
View prompt source

Context / Give the work a purpose
A small workshop project sets an appropriate scale. The initial idea gives the interview a starting point without pretending the decisions are already made.
Task / Ask for discovery
“Clarify this idea” is a different task from “build this website.” Say which mode of work you want before the agent takes action.
Method / Make room for decisions
One question at a time keeps the conversation manageable. Options help you decide, but the agent must not answer for you.
Constraints / Stop the wrong work
No technology choices, page structures, design, or file changes. These boundaries prevent the conversation from becoming an implementation session.
Verification / Check the brief
At this stage, verification is a content check—not a test command. Confirm a specific audience, primary job, coherent journey, and visible scope boundaries.
Deliverable / Define the stopping point
Seven headings give the output a predictable shape. “Stop after presenting the brief” prevents the agent from continuing into specification without approval.
Where are the references?

This is discovery from an initial idea, not implementation against an existing design. Add genuine event information if you have it; don’t invent references just to fill a template.

04 · The example artifact

What good looks like.

A fictional DesignCraft example, not a set of decisions you have already approved. Your own brief should reflect your answers and retain the questions you have not resolved.

Specific enough to discuss

One audience. One primary job.

The visitor journey explains why each capability belongs. The brief does not prescribe frameworks or detailed page layouts.

Bounded enough to build

“Not building” is part of the brief.

No payments, accounts, CMS, or admin dashboard. These exclusions prevent a small conference site from becoming an event-management platform.

Honest about uncertainty

Unresolved does not mean forgotten.

The RSVP service and photography still need decisions. Carry those questions into specification rather than letting the agent guess.

# DesignCraft 2026 — Idea Brief

## Description

DesignCraft 2026 is a one-day conference in Vancouver for people who design and build digital products.

## Audience

Product designers, design engineers, and design leaders working in technology.

## Primary job

Help prospective attendees understand the event and decide whether to RSVP.

## Main user journey

1. Learn what the conference is about.
2. Review the schedule.
3. Explore the speakers.
4. Submit an RSVP.

## In scope

- Event information
- Conference schedule
- Speaker information
- RSVP submission
- Responsive desktop and mobile experience

## Out of scope

- Payments
- User accounts
- A content management system
- An administrative dashboard
- Personalized schedules
- Real-time event updates
- A native mobile application

## Unresolved decisions

- Whether RSVP submissions require a real external form service
- Whether speaker photography will be provided or represented by placeholders
