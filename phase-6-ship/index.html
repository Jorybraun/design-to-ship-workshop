Phase 06 · Ship + handoff

Ship the reviewed build.
Leave a reliable handoff.

Choose the exact source and artifact. Approve one public target. Verify what visitors receive and give the next maintainer a usable recovery path.

01 · Say / do / decide

Name what is shipping.

Reviewed scope → source preview → artifact inspection → recovery plan → explicit deployment approval → hosted smoke test → maintenance handoff.

Confirm the product and release owner

Say: “Are we shipping this workshop teaching website or the DesignCraft conference app?” They are not the same product. website/ is workshop reference material, not a built conference app.

Do: identify actual approved scope, human owner, source of truth, current commit/branch and dirty tracked/untracked state. The example spec and candidate plan are fictional and unapproved. T1 still has destination shells.

Paste: Prompt 1 with exact read scope. Expect: a readiness report, revision-bound evidence and blockers, not a build. Check: actual evidence, environment and timestamp; missing checks stay NOT RUN.

Decide: continue to previews or resolve missing inputs. Stop: ambiguous product, unknown owner, unreviewed changes or invented approval.

02 · Source publication

Publish an intentional source package.

A human chooses owner, name, visibility and rights. A reviewed allowlist is safer than publishing the workspace or cloning private material wholesale.

Say / do / paste: preview the repository

Say: “Which exact files may become public, under whose ownership?” Do: name owner/account, repository name, visibility and default branch. Review source, history, Markdown, images, logos, fonts, attribution and reusable skills for disclosure and redistribution rights.

Paste: Prompt 2. Expect: file-by-file allowlist, exclusions, exact operations, README setup/update instructions and maintainer ownership. The human selects a license or resolves publication without an open-source license; never add one automatically.

Check: ignore dependencies such as node_modules/, dist/, caches, environment files, secrets, local .devin configuration and outputs/. Ignore rules do not remove tracked files or old secrets. Inspect the actual content and any history to be published.

Existing lessons link project-local skill source. Individually reviewed reusable skills may belong in the public source allowlist; that is not permission to expose the entire .devin directory. Never use broad git add ..

Decide / check / stop: authorize one exact publication batch

Decide: explicitly approve or deny owner/name/visibility, file manifest and exact stage/commit/create/push operations. A supported repository tool, including GitHub CLI where available, does not confer permission. No staging, commit, repository creation or push before approval.

Check after approval: verify actual remote identity, visibility, default branch, commit and returned source URL. Ask the operator about missing access without revealing credentials. Stop: rights gaps, ambiguous failures or partial remote operations; reconcile state before retrying. Source publication never automatically deploys.

03 · Artifact inspection

Inspect what the host will receive.

A deployable artifact has its own identity and manifest. Neither the whole repository nor a directory named dist is automatically the correct release.

The workshop packaging catch

Say: “This manifest, not the laptop, is the release.” Do: inspect the root entry index.html, intended lesson paths, shared CSS/logo and downloadable Markdown or reviewed skill source. Keep internal maintenance tests out of deployment even if they belong in reviewed source.

Check: these lessons reference ../website/src/index.css and ../website/public/cognition-mark.svg. Preserve that approved relative layout or separately authorize and verify a path rewrite. Deploying only website/dist loses the lessons; deploying the entire root can expose private/internal files. Every intended public dependency must be in the artifact allowlist.

Expect: an artifact tied to reviewed source, with direct nested entry/reload and downloads accounted for. Exclude secrets, local configuration, dependencies, caches and unrelated outputs. Generated deployment assets need explicit approval; source ignores and deployable files are different lists.

Decide: approve any needed build/package command separately with working directory and generated outputs, then inspect the artifact and refresh evidence. Plain static HTML may need no build. Stop: missing entry page, unknown generated contents, broken paths or source/artifact mismatch. No packaging code is required to rehearse this lesson.

04 · Capability + permission

Prepare recovery. Approve one target.

A Devin URL is an option only when the actual session and account support native deployment. This local lesson-authoring CLI has no discovered native deploy tool.

What native deployment does—and does not promise

The official deployment capabilities guide describes native deployment for small standalone apps Devin creates. A static directory must contain index.html, whether produced by any framework or written as plain HTML. Success returns a unique public devinapps.com URL that stays available after the session ends; that is not a maintenance or service-level guarantee.

Do: have the operator inspect actual session deployment tools and account settings. Native deployment is available to non-enterprise organizations with secure mode OFF. Enterprise deployments are disabled and secure mode blocks deployment. Never disable security or change organizational policy to proceed.

Existing applications generally use their own approved CI/CD, credentials and pipeline. An existing static application may work natively, but compatibility is not guaranteed. No supported tool or access? Ask the operator, choose separately approved own hosting, or leave a manual prepared release. Do not invent commands or a hosted URL.

Say / do / paste: prepare rollback before deployment

Say: “Who can recover this target, and from which artifact?” Do: retain the reviewed artifact, manifest and evidence; name the recovery operator, trigger and host-supported procedure. Identify the prior known-good version. A first deployment has no previous version: prepare supported unpublish/disable or a reviewed fix-forward strategy instead.

Paste: Prompt 3 with exact target/account, artifact, commit/dirty-state evidence and manifest. Expect: preview only, supported capability/access findings, verification gaps, recovery strategy and a request for explicit session approve/deny. Rollback execution needs its own approval.

Decide / check / stop: deploy only the approved artifact

Decide: explicitly approve or deny this exact public target, artifact, commit and manifest, plus the relevant native deployment approval. Only after confirmation use available supported tools for that package alone. No automatic install, configuration change, extra service, credential disclosure or cloud launch.

Check: actual returned public URL, deployment ID if available, target/artifact evidence and timestamp. Localhost and browser previews are not substitutes. Stop: partial errors or unclear remote state; resolve before retrying. Do not change Git or trackers.

Cloud /handoff is a separate launch, transfer and cost decision, not a deploy command. Review tracked/untracked transfer scope and follow Phase 5 cloud handoff; never launch it just to make deployment appear available.

05 · Hosted evidence

Test the URL visitors actually receive.

An upload success is not a verified release. Local browser evidence cannot prove hosted path behavior, asset availability or artifact identity.

Say / do / paste: run an approved, non-mutating smoke test

Say: “Use the actual returned public URL, not the source repo or local preview.” Do: approve that URL and exact non-mutating interactions. Use fictional data only; do not send or repeat real registrations, emails, purchases or other live actions. Uncertain side effects block submission.

Paste: Prompt 4. Expect: PASS / FAIL / NOT RUN per check with revision, artifact, environment, timestamp and evidence. Compare source-to-artifact-to-host identity using available capabilities; label unverifiable matches.

Check: entry, navigation, every intended nested path by direct URL and reload, unknown-path behavior, missing assets and intended Markdown/skill downloads. At 1440px and 375px inspect mobile layout, overflow, expanded disclosures, keyboard reachability, visible focus and new console errors.

Check privacy: the workshop needs no backend. If a reviewed conference demo includes RSVP, verify its disclosure and approved network/storage/console evidence: no requests, persistence, entry logging or analytics payloads. Example D2/I6 forbids sending or saving; no real RSVP backend is implied.

Decide: accept evidence or request a bounded correction/recovery for separate approval. Stop: public leakage, harmful side effects, broken critical paths or unexplained identity mismatch. Report the owner and urgency; do not silently redeploy or rollback.

06 · Release + maintenance

Leave enough to update and recover.

The next maintainer needs source code, precise release evidence, verified update commands and named owners—not a secret dump or an optimistic summary.

Say / do / expect: make the handoff usable

Say: “Could someone maintain this without our chat?” Do: review Prompt 4's chat handoff against the template below. Distinguish source URL and deployed URL; record approved scope, commit/dirty state, artifact manifest, target/deployment identity, approvals, evidence and known gaps.

Expect: verified update/build/check commands with working directory and allowed outputs; maintainer and access-management owner, approved access method without secrets, maintenance cadence, issue intake and next bounded action. Record recovery operator, trigger, prior good artifact or first-release strategy, target and required approval.

Check: UNKNOWN and NOT RUN remain honest. No private transcripts, local machine paths or credentials in public handoffs. Decide: separately approve saving/sharing to an exact destination and audience. Stop: unknown ownership or unsupported recovery claims; do not auto-update Git, documentation or trackers.
